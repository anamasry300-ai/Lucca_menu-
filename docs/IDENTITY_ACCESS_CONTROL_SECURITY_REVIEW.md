## 1. ملخص النتائج

التغييرات المُضافة **سليمة في أغلبها** وتحقّق الإغلاقات المعلنة (D-01/D-03/D-04/D-05/D-06/D-08 وD-07 جزئياً) فعلياً على الخادم، وقد نجحت جميع الاختبارات الحالية (17 حزمة + 1 جديدة = 18). لكن المراجعة أثبتت **ثغرتين عاليتين (HIGH) لم تُغلَـقا**:

1. **`POST /api/sync` يتجاوز فحص سلامة الأموال (D-02)** بشكل كامل: دور محدود (كاشير/جهاز/مطبخ يملك `sync`) يستطيع إدخال طلب بأصناف بسعر **سالب** وإجمالي سالب، ثم `POST /api/orders/:id/checkout` ينجح ويكتب **صفّ دفعة بقيمة سالبة**. (أثبت ذلك عملياً — القسم 2.3).
2. **`GET /api/users` يُرجع عمود `password`** (هاش PBKDF2، أو نص صريح للبيانات القديمة) لأي هوية مسموح لها بالقراءة = `admin` **و`manager`** (وإنشاء الكاشير المصرّح). تسريب أسرار اعتماد. (أثبت ذلك عملياً — القسم 2.2).

**القرار النهائي: لا يُعلَن PASS.** توجد ثغرتان بدرجة HIGH (إحداهما قد تُصنّف BLOCKER في نظام مالي). كما توجد ثغرات MEDIUM/LOW مؤكدة (تعديل سعر=0 عبر CRUD، `changeAmount` غير محدود، غياب فحص `total>0` في مسار الدفع غير المقسّم).

| المحور | التقييم |
|--------|---------|
| مصادقة/تفويض على الخادم | ✅ سليم (لا اعتماد على دور يرسله المتصفح) |

| D-06 حذف users/audit_logs | ✅ admin فقط |

| D-04 شاشة المطبخ | ✅ بلا anon؛ عبر جلسة |

| سرّية الاعتماد | ⛔ **`GET /api/users` يكشف `password`** لـmanager |

## 3. الثغرات المؤكدة (مسار الملف + رقم السطر)

### F-1 (HIGH / مرشّح BLOCKER) — `/api/sync` يتجاوز سلامة الأموال وتُنتج دفعات سالبة
- مسار الكتابة: `backend/src/index.ts:1017-1048` (الحاجز يفحص فقط الحالة النهائية ومطابقة `total` لإجمالي **الوارد**، ولا يفحص السعر/الكمية). البند الحاسم: `index.ts:1039-1047`.
- فحص الأموال `validateOrderMoney` **محصور بمسار CRUD فقط**: `backend/src/routes/crud.ts:186-209`، مُطبّق في `crud.ts:360` و`crud.ts:516`.
- إعادة حساب الإجمالي في الدفع تتبع `items` المخزَّنة (`index.ts:447-457`) — إن كانت سالبة يبقى الإجمالي سالباً.
- مسار الدفع غير المقسّم بلا فحص إيجابية: `index.ts:539-542` → تخزين `totalPaid` في `index.ts:563-566` → إدراج الدفعة `index.ts:587-590`.
- الأثر: دور محدود (cashier/device/kitchen يملك `sync`) يُدخل طلباً سالباً، ثم (cashier/device) يُغلقه بدفعة سالبة — تلاعب مباشر بالسجل المالي والتقارير (`SELECT SUM(total)`).

### F-2 (HIGH) — تسريب عمود `password` لمدير النظام عبر `GET /api/users`
- `backend/src/routes/crud.ts:272` (`SELECT *`) + `backend/src/routes/crud.ts:55` (`readDenied` يسمح لـmanager) + `backend/src/routes/crud.ts:279-292` (نفس المشكلة للمورد المفرد).
- دعم كلمة المرور النصية القديمة: `backend/src/auth.ts:57-60` ⇒ قد يُعرض سرّ فعلي لا هاش فقط.
- الأثر: أي `manager` (أو admin) يسحب أسرار اعتماد كل المستخدمين — قابل لإساءة الاستخدام الداخلية وإعادة الاستخدام.

### F-3 (المرتفعة المتبقية لـD-02) — سعر الصنف يمكن خفضه (بما فيه 0) عبر CRUD
- `crud.ts:194-201` يسمح بأي سعر `0 ≤ price ≤ MAX_ITEM_PRICE`؛ لا ربط بالكتالوج.
- مُثبت عملياً: POST price=0 → 201 (total=0)؛ PUT price=0 → 200.
- الأثر: كاشير يخفض الإجمالي تعسّفياً قبل التحصيل (سرقة مباشرة). هذا هو جوهر D-02، وهو **مؤجَّل موثَّقاً** إلى P5 لكنه ما يزال قائماً.

### F-4 (MEDIUM) — `changeAmount` يُقبل من العميل بلا حد أعلى
- `backend/src/index.ts:565` (تخزين `changeAmount` كالمُرسل)، والتحقق الوحيد هو عدم التحقق.
- مُثبت: `changeAmount=999999999` → مخزَّن كما هو.

### F-5 (MEDIUM) — مسار الدفع غير المقسّم لا يفرض `total > 0`
- `backend/src/index.ts:514-542`: المسار الفردي يستخدم `total` مباشرة؛ لا رفض للصفر/السالب (المسار المقسّم يرفض `amount ≤ 0` عند `:490`).
- العلاقة بـF-1: يُمكن إغلاق طلب سالب/صفر بدفعة مقابلة.

### F-6 (LOW/MEDIUM) — DOM XSS محتمل في شاشة المطبخ
- `kitchen.html:529-540` و`kitchen.html:557-567`: بناء HTML عبر `innerHTML` بحقول غير مُهرَّبة (`item.name`, `note`, `customerNotes`, `tableId`, `orderNum`).
- السياق الآن موثَّق (جلسة Electron + `apiRequest`) → أي XSS يستدعي API باسم المستخدم. (نمط موجود مسبقاً، لكنه تضخّم مع ربط الجلسة.)

### F-7 (LOW) — فتح المطبخ غير موثَّق في سياق المتصفح
- `index.html:1371`: fallback `window.open('kitchen.html')` خارج Electron يفتح الصفحة بلا جلسة (لا وصول خادمي لغياب الرمز، لكنها تقرأ IndexedDB المحلي). القيد غير مؤكَّد في بيئة Electron فقط.

### F-8 (LOW) — اتساق إعادة الفتح مع الاستردادات
- `index.ts:781-785` يُصفّر `refundAmount`/`voidedAt` ويحوّل الحالة إلى `pending/unpaid`، لكنه **لا يلمس صفوف `refunds` السابقة**؛ سقف الإلغاء لاحقاً يقرأ مجموع `refunds` (`index.ts:675-680`) ⇒ تعارض محتمل بين رصيد الاسترداد والطلب المُعاد فتحه. (منطق أعمال، لا تصعيد صلاحيات.)

### F-8b (LOW) — `DELETE /api/settings/:id` ما زال ممكناً للمدير
- `crud.ts:609` (`deleteDenied` = admin/manager) و`settings` ليست في `DELETE_ADMIN_ONLY` (`crud.ts:84`) — no-op لكن سطح إدارة إضافي.

## 4. المخاطر التي لم يُمكن التحقق منها

1. **K-04 / RLS السحابي**: نتائج SQL Editor الحيّة لسياسات Supabase غير متوفرة؛ سلوك anon كان مفتوحاً سابقاً ولا يمكن تأكيد إغلاقه من هنا.
2. **الوضع السحابي (`luccaDataMode==='supabase'`)**: مسارات `LuccaDB.Orders.void`/sync السحابية لم تُختبر (البيئة المعزولة تستخدم خادم Node/SQLite فقط).
3. **زمن تشغيل Electron/IPC**: لم يُشغَّل Electron فعلياً؛ تحقق `open-kitchen` اقتصر على فحص المصدر + منطق `session-manager` (المقروء).
4. **المُحدِّث الذاتي (electron-updater / GitHub)**: مصدر التحديث وثقة القناة خارج نطاق هذه التغييرات ولم يُراجَع.
5. **مدى انتشار كلمات المرور النصية القديمة** في قواعد الإنتاج (يحدد خطورة F-2 فعلياً).
6. **سلوك التزامن الفعلي من العملاء** (شكل `items` كسلسلة JSON) — أثبتنا أن السلسلة تُقبل والمصفوفة تفشل؛ يفترض أن العميل يرسل السلسلة كما في المسبار.

## 5. تقييم تأجيل ربط سعر الكتالوج (catalog price binding → P5)

- **مبرّر تقنياً**: حمولة الطلب من الواجهة (`buildOrderPayload`) لا تحمل `productId`، والنظام يدعم `originPrice`/variations وأصنافاً حرة — إذن الربط الكتالوجي يحتاج تغيير عقد الحمولة (P5). التأجيل معقول **بشرط** إغلاق البدائل الرخيصة الآن.
- **غير مقبول الحالة الراهنة**: التأجيل صحيح، لكن «سلامة المال» المزعومة لا تُطبَّق على `POST /api/sync` (F-1)، ومُثبت إنتاجه **دفعات سالبة**. أي إعلان «مغلق D-02» غير دقيق.
- **الحد الأدنى المطلوب قبل Commit** (لا يحتاج productId): تطبيق `validateOrderMoney` (سعر/كمية غير سالبين + سقف + خصم منطقي) على كل مسار كتابة الطلب (sync + crud)، وفرض `total > 0` و`0 ≤ changeAmount ≤ amount` في التحصيل. الربط بالكتالوج الكامل يبقى P5.

## 7. الإصلاحات المطلوبة قبل Commit

1. **(F-1)** تطبيق فحص سلامة الأموال على مسار `POST /api/sync` للطلبات: رفض سعر/كمية سالبة أو تتجاوز السقف، ورفض/تعقيم الإجمالي السالب — بنفس منطق `validateOrderMoney` (يُنقل إلى وحدة مشتركة لتُستدعى من sync وcrud).
2. **(F-1/F-5)** فرض `total > 0` في مسار التحصيل غير المقسّم (`index.ts` ~514-542)، ورفض كتابة أي دفعة `amount ≤ 0` (المسار الفردي مثل المقسّم).
3. **(F-2)** حجب عمود `password` (و`syncId` غير الضروري) من `GET /api/users` و`GET /api/users/:id` — قائمة أعمدة آمنة أو redaction في `parseRow`، مع منع `SELECT *` لهذا المخزن.
4. **(F-4)** تقييد `changeAmount` من العميل (≥0 و≤ المبلغ المُسلَّم − الإجمالي) وعدم الثقة به مباشرة.
5. **(F-3)** كحد أدنى مؤقت (قبل P5): أرضية/سقوف واقعية لكل صنف (أو ربط بالكتالوج) — لا يُترك الرقم لحمولة العميل تماماً.
6. **(F-6)** ترميز مخرجات kitchen.html (textContent/createElement بدل innerHTML) أو تعقيم مركزي.
7. **(F-10)** توسيع `phase8` ليشمل مسار sync ودفعات سالبة، وتشديد فحص رفض الكاشير تحديداً (نوع المخزن/الفاعل).
